## Wave 1 — Diary Archive + Publishing (DONE)

**Branch:** `feat/diary-archive-and-publish`
**Spec:** `docs/superpowers/specs/2026-04-26-diary-archive-and-publish-design.md`
**Plan:** `docs/superpowers/plans/2026-04-26-diary-archive-and-publish.md`

### What it does

- SQLite (`~/.reachy-claw/reachy.db`, WAL mode) replaces the jsonl event logs.
  Tables: `asr_events`, `emotions`, `faces`, `thoughts`, `sensors`
  (provisioned for Wave 3, currently empty), `diaries`.
- `DailyLogPlugin` writes events to SQLite.
- One-time migration `scripts/migrate_jsonl_to_sqlite.py` imports legacy data.
- `scripts/generate_diary.py` queries SQLite for a day, asks the LLM
  to compose Markdown with **Astro `docs` collection** front matter
  (`title`, `title_en`, `date "YYYY.MM.DD"`, `category: "Reachy 日记"`,
  bilingual description, coverImage URL, tags, etc.). Markdown body has
  three fixed Chinese section headings: `## 今天的心情` / `## 遇到的人` /
  `## 想到的事`. Stored in the `diaries` table.
- `scripts/publish_diary.py` clones the site repo via SSH deploy key,
  drops the .md into `src/content/docs/<date>-reachy-diary.md`, copies
  capture images to `public/captures/<date>/`, commits + pushes.
- Privacy linter: blocks publish if any verbatim user-ASR substring
  ≥20 chars appears in the body.
- Dashboard endpoints `/api/diaries`, `/api/diary/{date}`, `/api/diary/latest`
  read from SQLite (parse Markdown front matter into the JSON shape
  `diary.js` expects).

## Wave 2 — Rest Window + Settings Panel (DONE)

**Branch:** `feat/rest-and-settings-panel`
**Spec:** `docs/superpowers/specs/2026-04-27-rest-and-settings-panel-design.md`
**Plan:** `docs/superpowers/plans/2026-04-27-rest-and-settings-panel.md`

### What it does

- **RestPlugin** polls every 30s. When the local clock enters the
  configured window (default 23:00–24:00 Asia/Shanghai), it emits
  `rest_start` (and `rest_end` on exit). Each plugin gates its hot loop:
  ConversationPlugin (ASR/LLM/TTS), FaceTrackerPlugin, VisionClientPlugin,
  MotionPlugin. ConversationPlugin additionally cancels any in-flight
  LLM task and drains TTS.
- **ZMQ control PUB** on `tcp://0.0.0.0:18791` for remote vision containers.
  RestPlugin sends `{"cmd":"pause"}` / `{"cmd":"resume"}`. `vision-hailo`
  and `vision-stub` producers subscribe via env `REST_CTRL_URL` and gate
  their inference loops. To defend against the slow-joiner problem, RestPlugin
  re-emits `pause` every 30s tick while resting — a container that restarts
  mid-rest converges within one tick.
- **HousekeepingTask registry**. v1 ships `DiaryGenerateAndPublishTask`
  which subprocess-runs `generate_diary.py` + `publish_diary.py`. Hard cap
  10 minutes per task (kills + waits child on cancel). Future: vacuum,
  cover-image generation, log rotation.
- **Settings persistence reuses the existing `runtime-overrides.yaml`
  mechanism** (same as `dashboard_volume`). Decision rationale: the project
  already has a runtime-tunable persistence path; adding a SQLite settings
  table would have been a duplicate mechanism. We keep SQLite for event-stream
  data only.
- **Dashboard integration**: rest + diary live inside the existing gear-icon
  modal (NOT a new top-level page).
  - `General` tab: Rest Window section (right-aligned toggle, 24h text-mode
    HH:MM inputs, force-state badge, `Force Sleep` / `Force Wake` /
    `Follow Schedule` buttons, separate Timezone row).
  - `Diary` tab: auto-publish + privacy-linter toggles, site repo URL/path/branch
    inputs, 14-day history with per-row Generate/Publish/Regenerate buttons.
  - `Prompt` tab: existing Conversation/Monologue/Interpreter prompts plus
    new **Diary Prompt** textarea (default sourced by parsing
    `scripts/generate_diary.py`'s `SYSTEM_PROMPT` constant — single source
    of truth, cached on first request).
- **Force controls** call `POST /api/rest/force` with `{"action":"enter"|"exit"|"clear"}`.
  A user can manually drive the system into rest for testing or ad-hoc
  housekeeping. `_force_state` (True/False/None) overrides the schedule
  until cleared.
- **Status endpoint** `GET /api/rest/status` returns:
  ```json
  {"resting": bool, "started_at": int|null, "force_state": true|false|null,
   "enabled": bool, "window_start": "HH:MM", "window_end": "HH:MM",
   "timezone": "IANA", "plugin_paused": {"motion": bool, "conversation": bool, ...}}
  ```
  The dashboard polls this every 5s while the modal is open.

### Codex review caught (and fixed)

1. HHMM regex was accepting `24:30` (silently mod-24'd to `00:30`); now rejects
   `24:01..24:59`, only `24:00` is the end-of-day sentinel.
2. ZMQ slow-joiner: heartbeat re-emit while resting.
3. `_run_subprocess` now kills + waits child on `CancelledError` (no orphans).
4. Diary trigger handlers return **HTTP 409 in-progress** on concurrent
   same-date generate/publish (was: queue behind a lock).
5. ConversationPlugin cancels `_active_llm_task` on `on_rest_start`.
6. Cross-field validator rejects degenerate `rest_window_start == rest_window_end`
   (unless end is `24:00`).
7. Tests added: 24:30 reject, 24:00 accept, concurrent 409, degenerate 400,
   runtime-overrides reload on fresh `Config` load.
8. `save_runtime_overrides` non-atomic write documented as a pre-existing
   follow-up (out of scope for this branch — would be a 5-line patch:
   write to `.tmp` then `os.replace`).

## Wave 3 — HA Sensor Sync + Config Panel (NEXT — not started)

### Confirmed user intent (from this session)

> 应该有个面板去拉取这个数据。通过面板去配置要对接哪些 HA 数据，并且
> 在这个面板上还要配置：
> 1. HA 相关的 IP 地址
> 2. Token
> 3. 这个注入哪个，你就让 prompt 里面自己定义就好了嘛

**Crucial design decision**: do NOT bake in semantic mappings ("this entity
is weather, that one is occupancy"). Just ingest raw entity values into the
`sensors` table; the diary LLM gets all of them and the user's
**Diary Prompt** (already configurable from this wave) decides how to
interpret them.

### Approach (HA pull, not push)

Reachy actively polls Home Assistant's REST API. Cleaner than push
(no need to expose Reachy to HA's network with auth, no inbound endpoint).

### Branch

`feat/ha-sensor-sync` — based on `feat/rest-and-settings-panel`.

### Planned scope

1. **`HASyncPlugin`** in `src/reachy_claw/plugins/ha_sync_plugin.py`
   - Reads from `app.config.ha_*` fields (new):
     - `ha_url: str = ""` (e.g. `http://homeassistant.local:8123`)
     - `ha_token: str = ""` (long-lived access token)
     - `ha_sync_interval_s: int = 300` (5 minutes)
     - `ha_entities: list[str] = []` (entity_ids to sync; empty = no sync)
   - Loop: every interval, for each entity, GET `<ha_url>/api/states/<entity_id>`
     with `Authorization: Bearer <token>`. Parse response, write to
     `sensors` table:
     - `source = "ha"`, `key = entity_id`, `value_num = float(state)` if
       parseable, else `value_text = state`. Attributes can be flattened
       into additional rows (e.g. `<entity>.attr_name`) — keep this
       simple in v1, just the main state.
   - Subscribe to `rest_start` / `rest_end` and pause polling during rest
     (consistent with other plugins).
   - On request failure: log, skip that entity for that tick, retry next tick.

2. **API endpoints** in `dashboard_plugin.py`
   - `POST /api/ha/test` — body `{"url", "token"}` (or use saved values
     if omitted) → probe `<url>/api/` with auth header → 200/401/timeout.
   - `GET /api/ha/entities` — proxy to `<ha_url>/api/states`, return list
     of `{entity_id, state, attributes.friendly_name, domain}` grouped
     by domain in the response shape so the front-end can render a tree.
     Uses saved config; returns 400 if unset.
   - These are protected by being on the dashboard server only (local network).

3. **Settings tab `HA Sensors`** in dashboard
   - Sections (use existing `detail-section` / `toggle-row` styles for
     consistency with Diary tab):
     - **Connection**: URL input, Token input (password mode + show/hide
       toggle), interval slider, "Test Connection" button (calls `/api/ha/test`,
       shows result inline).
     - **Entities**: "Refresh" button → `/api/ha/entities` → display
       grouped checkboxes (collapsible by domain). Each row: checkbox +
       `entity_id` + current `state` + `friendly_name`. Save commits the
       checked list to `ha_entities` via `PUT /api/settings/ha`. The
       settings_schema registry needs new entries for `ha.url`, `ha.token`,
       `ha.sync_interval_s`, `ha.entities` (list type — extend the
       schema validator to accept list[str]).

4. **`generate_diary.py` enhancement**
   - Pass through to LLM: bundle current day's `sensors` rows alongside
     existing `asr_events`/`emotions`/`faces`/`thoughts`. Group by `key`,
     emit `[{ts, key, value}]` array per key (or just a flat list — let
     the prompt cope).
   - The script already accepts everything the LLM uses via the user prompt
     so this is just an addition to `_build_user_prompt` (or
     `events_for_day`'s output bundle).

5. **Tests**
   - `tests/test_ha_sync_plugin.py` — mock httpx, fake HA responses, assert
     rows land in the SQLite table.
   - `tests/test_ha_api.py` — `/api/ha/test` 200/401, `/api/ha/entities`
     proxy, settings PUT for `ha.entities` (list type).
   - `tests/test_settings_schema.py` extension — list validator.
   - Frontend: manual.

### Open design questions to resolve in brainstorm

- **Token storage**: just `runtime-overrides.yaml` like other strings, OR
  a separate `~/.reachy-claw/secrets.yaml` with `chmod 600`? (HA tokens
  are powerful — read all device states, control devices.) Lean toward
  separate file with `0600` perms for the principle, but yaml override
  is consistent with everything else.
- **Polling cadence under rest**: skip the whole rest window? Or just
  skip the active rest minutes and resume? Probably skip during rest,
  resume on `rest_end`. Simplest implementation.
- **Attribute flattening**: e.g. `weather.home` has `temperature`,
  `humidity`, `wind_speed` as attributes. v1: ignore attributes
  (state only). v2: flatten if user opts in per entity. Recommend
  defer to v2 to keep the first cut tight.
- **Sensor row volume**: 5-min polling × 50 entities = 14400 rows/day.
  Tens of MB/year. Same order as existing event tables. Ops fine.
- **Diary prompt training**: provide a default Diary Prompt template
  with a "Available sensor keys today: ..." section and example usage,
  so users don't have to reverse-engineer the schema. Maybe ship a
  preset selector ("Atmospheric / Activity-aware / Minimal") in a v2.
